01

PRD + Spec 标准，生成 Workspace

把需求和本标准包一起交给能读取并生成文件的 AI。

必需：你的 PRD / IPO

谁使用、输入什么、按什么规则处理、输出什么、怎样算完成。

可选：已有项目与规范

存量代码、企业 UI / 编码规范、输入样本和输出样例。有就一起给。

第一次做项目：提供 PRD + 标准 ZIP。没有代码也能初始化，不要先写业务代码。

这次放入 AI 的材料

PRD／IPO + Spec 标准 ZIP；其他资料按需补充。

查看本模式完整提示词


本网页只组织提示词，不调用模型、不上传资料、不保存输入。复制后粘贴到 AI 中执行。客户端不能读 ZIP 时，先解压并打开实际文件夹。


第一步到这里就停：拿到项目专属 ZIP + HTML，查看范围、规则与缺口；不要把“文件生成了”当成“已批准开发”。


应得到候选 Workspace、可追踪的业务规格、验收设计、问题清单和下一步说明。默认状态为 BASELINE_DRAFT。




02
打开项目包，确认设计与计划
解压刚生成的项目 ZIP，在 Codex 中打开项目根目录，而不是继续在原模板里开发。


brainstormingwriting-plans


先读项目 AGENTS.md、当前 Spec 和待确认问题。已有业务答案直接沿用，只讨论真正未定的范围、规则、设计与授权。


确认当前设计后，生成逐任务实施计划。每个任务都写清修改哪些文件、先测什么、怎么运行、预期结果是什么；计划确认后再实施。


先检查 Superpowers 是否实际可用
已安装就检查名称与状态；未安装按当前客户端的官方说明完成安装授权。本标准 ZIP 不等于 Superpowers 已安装。文件指令模式和真实技能调用要分开说明。




查看完整提示词


应得到当前版本的设计确认、基线记录和可执行计划。自动检查不替代人工确认；不重复从零做一遍需求访谈。




03
按任务执行，把 TDD 放进每一轮
不是“应用写完再补测试”，而是每个功能都有一次可证明的测试循环。


executing-plans或 subagent-driven-developmenttest-driven-development


RED先测，看到正确失败
→
GREEN最小实现，使测试通过
→
REFACTOR重构，完整回归仍通过


默认由当前执行者按计划完成任务；确有子智能体能力时，才选子智能体执行方式。两种方式二选一，不同时改同一任务。


有 Git 项目时，在写代码前使用或验证隔离工作区；遇失败先用 systematic-debugging 找原因。缺依赖、语法错误或工具未运行，都不是有效的 RED。




查看完整提示词


应得到逐任务代码、失败与通过记录、完整回归结果，以及关联的需求和验收编号。没运行的测试继续标“未执行”。




04
Review：先找问题，再按范围修复
先核对是否符合 Spec，再检查实现质量、权限、异常和回归风险。


requesting-code-reviewreceiving-code-review


把批准的 Spec、实施计划、实际变更和测试证据交给审查者。评审意见要核实，有效问题再按 TDD 修复、复验。


只做 Review 时，不偷偷修改规格或代码。没有实际代码，只能做 Spec / Workspace 审查；没有独立审查能力，就明确标注“自审”。




查看完整提示词


应得到问题、依据、位置、影响、修复和复验记录。严重问题没有闭环，不能写“审查通过”。




05
用证据验收，不用“看起来没问题”
验证的是当前版本；验证后又改了代码，相关测试就需要重新执行。


verification-before-completionfinishing-a-development-branch · 有 Git 时


必须如实区分
已通过、失败、未执行、不适用。每个结论要能找到对应证据。
不能互相替代
结构检查≠业务测试；模拟数据≠真实系统；单账号≠多人权限。


运行完整测试、构建与关键业务用例，核对保存、读回、权限、重复导入、导出和恢复。外部接口未接通就写未验证，不编造成功回执或发布链接。




查看完整提示词


应得到当前快照的真实测试证据、未完成项和交付等级。发布、合并、推送、迁移与清空仍需要相应授权。




06
每次刷新，交付一对 ZIP + HTML
ZIP 是可继续工作的输入，HTML 告诉下一位使用者：做了什么、还缺什么、下一步怎么走。


模式做什么版本示例
新建PRD → 首次候选 Workspacev1.0.0-r001
迭代按影响范围更新；规格变更重新确认v1.0.1-r002
Review不改受审规格与代码，只增加评审记录v1.0.1-r003


保留旧包，绑定上一包的摘要；新增、修改、保留和移除都写进变更说明。代码与文档一起更新，真实业务数据不因刷新而重置。


内置工具生成同版本 HTML、文件清单与 SHA-256，并拒绝覆盖同名版本；它不负责理解 PRD、运行应用或自动批准。




应得到可独立交接的新 ZIP + 同版本 HTML。后续修改继续用这套流程，不需要重新从空白开始。

?
容易混淆的四件事
先分清“初始化、确认、执行、验收”。


这个 ZIP 是应用成品，还是用来生成项目的标准？
它是标准。先用你的 PRD + 标准包生成“你的项目 Workspace”，再进行确认与开发。包里的跨部门事项督办仅是完整课堂候选示例，不会自动成为你的业务。


PRD 不够完整，还能先生成吗？
能先生成候选包，并明确缺口、设计建议和影响。关键业务规则、权限、金额或对外动作没有确认时，不进入已批准状态。不能为了显得完整而编造答案。


是否保留了原来的 workspace-init？
重点继承了你提供的 rdc-sdd-workspace-init v0.5.2 中的初始化、只读发现、基线候选、评审与增量维护。原 Skill 本身不做 PRD 转完整项目规格；本版新增这层，并把实施衔接到 Superpowers，不伪称兼容原企业 Runtime。


有没有内置日丰规范或自动发布？
没有收到日丰正式UI/编码规范和已验收标杆代码，不能声称已经适配这些未提供的材料。生成时可加入你们的正式规范。发布、企业系统写回与真实数据迁移不是默认动作。
