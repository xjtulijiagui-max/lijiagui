阅读指南

00

先看懂 OpenSpec 的五种文档

OpenSpec 帮我们把“想做什么”写清楚，再按清单开发和检查。它不会代替人判断需求，也不是只写一份说明书。

本页以已经开发的培训管理系统为例。你可以把它看成一份带讲解的项目规格书：先了解业务，再看规则、设计、任务和验收。老师可以按左侧目录讲解，学生可以用每节的例子核对理解。

文档用大白话说本项目里的例子
proposal.md · 提案为什么做？这次做到哪里？管理课程、学员和账号；本轮不做收费。
specs/ · 功能规格系统必须表现成什么样？普通用户能看课程，但不能删除课程。
design.md · 技术设计准备用什么办法实现？页面用 Vue，服务用 FastAPI，数据存 SQLite。
tasks.md · 实施任务具体先做哪件事、后做哪件事？先认证，再课程，再学员和用户，最后联调。
主规格与 archive/ · 归档现在以什么规则为准？过去改过什么？主规格记录现行规则，归档保留已完成的变更。
本页的栏目是对 OpenSpec 文档的教学展开，不是新增一种 OpenSpec 目录规范。业务、字段、页面和验收都围绕同一组规格解释。

课堂讨论 / 学生自查

“用 SQLite 存课程”与“课程编号不能重复”，哪一句是设计，哪一句是规格？

查看参考答案

SQLite 是实现方法，放在技术设计；编号不能重复是用户能观察到的规则，放在功能规格。换数据库后，编号不能重复的规则仍应成立。

实际怎么做：打开项目，先盘点，不急着生成代码

  1. 老师先给学生仓库读取权限，学生在独立练习副本中打开项目根目录（能看到 frontend、backend、openspec）。
  2. 在 Codex 对话里粘贴下面的提示词，让 AI 只读盘点。
  3. 检查 AI 给出的真实路径；如工具缺失，先按它报告的缺项完成准备，不把未安装写成已可用。

提示词为什么这样设计

先写清所在项目和本轮动作，再限制为只读。这样 AI 不会把“了解项目”误解为重新初始化或重写代码。

复制给 AI 的提示词

在已打开项目根目录的 Codex 对话中使用；含【占位符】时先替换。以下为现在编写的教学模板，不是历史开发对话原文。

我正在学习培训管理系统，请先只读盘点当前工作区。
1. 阅读 README、openspec/config.yaml、openspec/specs/ 和已归档变更。
2. 说明 proposal、specs、design、tasks、archive 各有什么用，用“新增课程”举例。
3. 列出实际存在的文档路径、当前有效规则和历史变更；不要把归档任务当成待办。
4. 检查本机 OpenSpec CLI 与相关项目 skills 是否可用；不能运行就明确报告，不假设已安装。
5. 给出“已具备 / 缺少 / 下一步”清单。
此次不修改文件、不安装依赖、不初始化项目、不发布。
看什么结果，才能继续？

应得到真实文件路径和准备清单。抽查其中一个文件确实存在；未解决的工具问题要保留。确认无误后进入提案。

结果不对时，如何追问

如果报告了不存在的文件，回复：“请重新核对实际目录，删除猜测内容，并列出无法读取的路径。”

PROPOSAL · 项目提案

01

为什么要做这个系统

假设老师用表格记录课程、学员和账号，我们希望把这些资料集中到一个系统里管理。

1.1 谁来使用

管理员负责维护资料；普通用户负责查看资料。这里“学员”是一份档案，不等于可以登录的用户账号。

1.2 做到什么程度

本轮要做本轮不做
课程：新增、查询、编辑、删除报名、选课与排课
学员：维护档案、按学号或姓名查找考勤、考试与成绩
用户：账号、角色、密码重置收费、支付与财务
登录、权限、桌面打包与 Web 部署配置桌面与云端自动同步

1.3 输入、处理、输出

贯穿全页的例子：新增一门 Python 课程

输入：编号 PY-001、名称 Python 入门、讲师 王老师、课时 16。
处理：检查是否为管理员、字段是否合规、编号是否重复。
输出：保存成功后，课程出现在列表中；重新打开系统仍能查到。

这些都是教学示例，不是已写入系统的真实记录。

这一部分写清楚，就能回答：谁来用、解决什么事、这次包括什么、不包括什么。
课堂讨论 / 学生自查

“加一个学员报名某门课程的功能”是否属于本轮已经完成的内容？

查看参考答案

不属于。现有学员档案和课程独立，没有报名关系；应另建 OpenSpec 变更，先补规则、数据关系和验收场景。

实际怎么做：把业务要求整理成 proposal

  1. 先把使用者、目标、包含和不包含的功能写在一段文字里。
  2. 现有项目练习先做提案对照，不重新创建已经完成的 MVP。
  3. 老师检查范围后，真正的新需求才进入新的 OpenSpec 变更；变更名由本次需求决定。

提示词为什么这样设计

提示词需要同时给出目标和边界。只说“做一个管理系统”，AI 容易自行加入报名、收费等不在范围内的功能。

复制给 AI 的提示词

在已打开项目根目录的 Codex 对话中使用；含【占位符】时先替换。以下为现在编写的教学模板，不是历史开发对话原文。

请以本培训管理系统为例，讲解并核对 proposal：
业务目标：管理员维护课程、学员、登录用户；普通用户只查看课程和学员。
本轮范围：登录、权限、搜索分页、详情、增删改查。
不包含：报名、考勤、考试、收费和桌面云端自动同步。
请对照归档的 training-management-mvp/proposal.md，输出：
① 为什么做；② 谁使用；③ 本轮包含/不包含；④ 会影响哪些能力；⑤ 尚未确定的问题。
每项注明来自我的输入还是已有文件；缺失信息不要自行补成已确认事实。
这是课堂阅读练习，只输出说明，不创建重复变更、不修改代码。
看什么结果，才能继续？

应得到范围明确的提案说明。检查有没有擅自增加业务；只有范围和关键问题明确后，才能细化规格。

结果不对时，如何追问

范围太大时回复：“把本轮缩小到已列出的能力，新增建议单独放到后续事项，不写入当前承诺。”

SPECS · 业务流程

02

用户从登录到完成工作

业务流程说明“人怎样使用系统”，先不要急着讨论代码。

2.1 管理员的一次操作

  1. 准备账号：Web 开发版通过命令创建首个管理员；桌面版首次启动时在页面设置。
  2. 登录：输入用户名和密码，正确后进入课程页面。
  3. 新增课程：填写 PY-001、Python 入门、王老师、16，点击保存。
  4. 检查结果：列表出现记录；搜索 PY-001，打开详情确认信息。
  5. 修改或删除：修改后检查新值；删除先出现确认，取消不应改变数据。
  6. 退出：退出后不能继续访问受保护的数据。

2.2 普通用户的一次操作

管理员创建普通用户账号 → 普通用户登录 → 查看课程或学员 → 搜索与查看详情 → 退出。普通用户不能进入用户管理，也不能新增、编辑或删除课程和学员。

2.3 遇到问题时

遇到的情况系统应该怎样处理
密码错误提示登录失败，不进入业务页面。
会话过期，也就是本次登录资格失效返回登录页面，让用户重新登录。
搜索不到 PY-999显示没有匹配记录；这不是系统故障。
网络请求失败显示错误并允许重试，不伪装成保存成功。
课堂讨论 / 学生自查

找不到课程和网络出错，为什么不能显示同一个空列表？

查看参考答案

前者是查询成功但没有结果；后者是没有拿到结果。混在一起会让用户误以为资料被删除。

实际怎么做：把需求拆成正常流程和异常分支

  1. 选一个具体角色和一项任务，例如管理员新增课程。
  2. 按登录、填写、提交、反馈、查询结果逐步写出动作。
  3. 补上错误密码、重复编号、网络失败、取消删除等分支。

提示词为什么这样设计

提供一个具体例子能避免泛泛而谈；要求异常分支，才能发现需求遗漏。

复制给 AI 的提示词

在已打开项目根目录的 Codex 对话中使用；含【占位符】时先替换。以下为现在编写的教学模板，不是历史开发对话原文。

请对照当前主规格，为“管理员新增 PY-001 / Python 入门 / 王老师 / 16 课时”写业务流程。
每一步用表格列出：前置条件、用户动作、系统响应、成功后去哪、失败时怎么办。
再写普通用户查看课程的流程。
补充未登录、编号重复、非法课时、网络失败和取消删除的分支。
区分已有规则与缺失规则；发现缺口只列问题，不改规格或代码。
最后用不超过三句话解释“查询为空”和“请求失败”的区别。
看什么结果，才能继续？

应得到顺序完整的流程表。学生应能照表模拟操作，且知道每个失败分支如何结束。

结果不对时，如何追问

步骤跳跃时回复：“请展开从点击保存到显示结果之间的动作，不要省略权限、字段检查和错误反馈。”

SPECS · REQUIREMENT / SCENARIO

03

把一句需求写成可检查的规则

Requirement 是“必须遵守的规则”；Scenario 是“在某个具体情况下，应该发生什么”。

3.1 先认识 WHEN / THEN

WHEN 就是“当……发生时”；THEN 就是“系统应当……”。SHALL 表示“必须”，不是“最好能做到”。

需求：管理员可以新增课程。

只有这一句还不够。还要说清：填哪些内容？编号重复怎么办？保存后会不会丢？谁没有权限？

3.2 课程规格的教学拆解

规则具体场景 WHEN预期结果 THEN
有效课程可以保存管理员填写完整资料，编号尚未使用保存成功，获得记录 ID，之后可查到。
编号不能重复再次新增编号 PY-001拒绝保存，原课程不被覆盖。
课时必须为正整数填 0、-1 或 1.5拒绝保存，提示输入不合法。
课程必须持久保存关闭服务后重新启动，再查询原课程仍然存在。
普通用户只有读取权普通用户尝试新增课程拒绝写入，不产生记录。
展开：真实 OpenSpec 写法示例
### Requirement: 课程管理
系统 SHALL 允许管理员新增、查看、修改、删除课程。

#### Scenario: 新增并持久保存
- **WHEN** 管理员提交有效课程
- **THEN** 返回 201 和课程 ID，服务重启后仍可查询

这里 201 是接口表示“创建成功”的状态码。规格原文还规定了字段和错误情况，此处只截取一个场景帮助理解。

3.3 三个模块分别负责什么

模块可以做的事容易混淆的边界
课程维护编号、名称、讲师、课时与描述；查询详情不是选课系统，也不记录报名人数。
学员维护学号、姓名、电话、备注；查询详情新增学员不会自动生成登录账号。
用户创建账号、修改角色、重置密码、删除账号不是学员档案；不展示密码或密码哈希。
课堂讨论 / 学生自查

请把“学号不能重复”写成 WHEN / THEN。

查看参考答案

WHEN 管理员提交已经使用的学号；THEN 系统拒绝新增并提示冲突，已有学员记录保持不变。

实际怎么做：将每条规则写成 Requirement 和 Scenario

  1. 先写一句必须成立的业务规则，不写技术实现。
  2. 为规则补充正常、异常和权限场景，用 WHEN / THEN 表达。
  3. 将场景与主规格逐条对照；教学新增编号仅用于课堂追踪，不能冒充原文编号。

提示词为什么这样设计

规则、场景、预期结果要分开。要求可以观察到的结果，避免“体验良好”“安全可靠”等无法直接验收的句子。

复制给 AI 的提示词

在已打开项目根目录的 Codex 对话中使用；含【占位符】时先替换。以下为现在编写的教学模板，不是历史开发对话原文。

请阅读 openspec/specs/courses/spec.md，按 OpenSpec 的 Requirement / Scenario 结构讲解课程规格。
逐条列出：规则原意、通俗解释、WHEN 条件、THEN 结果。
重点覆盖：有效新增、重复编号、空名称、非正整数课时、普通用户写入、重启后仍可查询。
保留 SHALL、Requirement、Scenario、WHEN、THEN 的结构含义。
如为了教学增加 REQ-C01 等编号，请明确它是本次教学编号，不是仓库已有编号。
输出教学对照稿，不改主规格。没有证据的规则列为待确认。
看什么结果，才能继续？

每条规则应至少对应一个具体场景，结果能够被检查。重复编号拒绝保存，不能被写成覆盖旧课程。

结果不对时，如何追问

场景太笼统时回复：“把‘处理正确’改成具体返回结果、记录是否变化，以及用户能看到什么。”

SPECS · 字段与数据约束

04

每一项资料，到底怎么填

字段是表单里的一个输入项。数据约束决定什么可以保存，什么必须拒绝。

4.1 课程资料

字段 / 代码名例子规则
课程编号 / codePY-001必填，1–32 字符，不能重复。
课程名称 / namePython 入门必填，1–100 字符。
讲师 / instructor王老师必填，1–100 字符。
课时 / hours16整数，范围 1–2147483647。
描述 / description适合零基础学员可留空，最多 2000 字符。

4.2 学员资料

字段 / 代码名例子规则
学号 / student_noS-001必填，1–32 字符，不能重复。
姓名 / name张同学必填，1–100 字符。
电话 / phone留空也可以可空，最多 32 字符；当前未要求唯一或固定格式。
备注 / notes教学示例档案可空，最多 2000 字符。

4.3 登录用户

字段 / 代码名例子规则
用户名 / usernameteacher01必填，1–100 字符，不能重复。
角色 / roleadmin 或 user只有管理员、普通用户两种。
密码 / password由本人设置创建或重置时为 8–256 字符；不把真实密码写入作业。

系统还会自动生成 id（记录的内部编号）和 created_at（创建时间）。课程编号 PY-001 是业务编号，与系统生成的 id 不是同一项。

进阶：后端统一校验

普通字符串去掉首尾空白，密码保留原样；拒绝 null 和没有定义的字段。用户响应不包含密码或哈希。字段实现见 backend/app/schemas.py。

课堂讨论 / 学生自查

一名学员和一个登录用户都叫“张同学”，系统会自动把它们关联吗？

查看参考答案

不会。当前两类数据独立，姓名相同也不会自动建立关系。

实际怎么做：做出完整字段表

  1. 打开 schemas.py 和接口文档，核对每个表单字段。
  2. 写出含义、示例、类型、必填、长度、唯一性。
  3. 专门检查空值、空字符串、自动生成字段，以及学员与账号的区别。

提示词为什么这样设计

SPECS · 规则与权限

05

谁能做什么，必须写清楚

权限不能只靠“把按钮藏起来”。即使有人直接发请求，后端也必须检查身份。

操作管理员普通用户未登录
课程、学员列表和详情允许允许拒绝
课程、学员新增修改删除允许拒绝拒绝
用户管理与重置密码允许拒绝拒绝

5.1 三条管理员保护规则

  1. 不能删除当前正在使用的账号，避免把自己删掉。
  2. 不能删除最后一个管理员，否则没人能管理系统。
  3. 不能把最后一个管理员降为普通用户，理由相同。

5.2 密码与会话

会话可以理解为“登录后获得的临时通行证”。默认有效期为 8 小时。退出、重置密码或删除账号后，对应通行证失效；修改角色后，下一次请求就按新角色检查。

示例：用户原来是管理员。另一个管理员把他改成普通用户后，即使旧页面还显示某个操作按钮，后端也应拒绝他的写操作。

DESIGN · 技术设计

07

前端、后端、数据库怎样配合

可以把系统想成办事窗口：前端是窗口，后端是办理规则，数据库是保存档案的地方。

组成负责什么本项目采用
前端展示页面、收集输入、显示结果Vue 3、TypeScript、Element Plus；Vite 负责开发和构建。
后端检查身份、校验数据、执行操作Python + FastAPI。
数据访问层把程序里的操作转换成数据库读写SQLAlchemy。
数据库持久保存课程、学员、用户和会话SQLite，一个本地数据库文件。

7.1 点击“保存”之后发生什么

① 页面收集 PY-001 等字段
↓
② 向后端发送新增课程请求
↓
③ 后端检查登录、角色、字段和重复编号
↓
④ 合法数据写入数据库
↓
⑤ 后端返回结果，页面更新列表

7.2 接口是前后端约定的“办事入口”

请求大白话成功结果
GET /api/courses查课程列表200：查询成功。
POST /api/courses新增一门课程201：创建成功，返回记录。
PATCH /api/courses/{id}修改指定课程200：返回修改后的记录。
DELETE /api/courses/{id}删除指定课程204：成功，无返回内容。

{id} 要换成真实记录 ID。接口不是都能直接在地址栏调用；登录与写操作还涉及会话和来源校验。

进阶：如何读错误状态码
代码含义例子
401身份无效未登录或登录已过期。
403不允许操作普通用户尝试写入，或请求来源不允许。
404找不到查询已删除的记录。
409冲突编号重复，或触发管理员保护。
422输入不符合约定课时为 0，或字段长度超限。

源码位置：课程接口在 backend/app/routers/courses.py，统一字段校验在 backend/app/schemas.py；更多约定见 docs/api.md。

TASKS · 实施任务

规格告诉我们“必须达到什么效果”，任务告诉我们“为了达到效果，要做哪些工作”。

顺序实际要做完成时检查
1. 工程基础建立 frontend/ 和 backend/，连通页面与服务前端构建通过，健康检查能访问数据库。
2. 登录与权限创建管理员、实现登录退出和角色检查错误密码不能登录，普通用户不能写入。

5. 用户管理账号维护、角色修改、重置密码不能删除自己，不能留下零个管理员。
6. 联调与交付全量测试、备份恢复、说明、归档记录实际通过项和未验证项。

做完之后，留下什么给下一位同学

OpenSpec 的收尾，是让规则、代码、测试和交付说明保持一致。

10.1 为什么要归档

  1. 核对任务是否完成，保存验收结果。
  2. 把本次新增或修改的规则同步到主规格。
  3. 把变更放入 archive，保留“当时为什么改、怎么改”的记录。
  4. 提交代码和说明，便于别人继续开发。

本项目归档了两个变更：业务 MVP（24 项任务）与桌面交付（8 项任务）。归档不是删除资料，更不是自动证明已经部署上线。

数据在哪里用户目录下的 SQLite 文件服务端数据库或持久卷。

10.3 本页、业务系统、源码仓库不要混淆

本页是可公开阅读的教学资料；业务系统是需要启动后端的培训管理应用；源码仓库保存代码与规格。GitHub Pages 上显示了本页，不表示 Python 后端也已经上线。

提交一份课堂作业时，建议附上：需求范围、规则与场景、数据字段、设计说明、任务完成情况、实际验收结果，以及未完成项。不要提交真实密码或真实学员资料。

提示词为什么这样设计

完成、归档、打包和上线是不同结果，提示词要分别要求证据，避免“归档成功”被写成“系统已上线”。

复制给 AI 的提示词

在已打开项目根目录的 Codex 对话中使用；含【占位符】时先替换。以下为现在编写的教学模板，不是历史开发对话原文。

请收尾已完成的 OpenSpec 变更【填写实际变更名】。
1. 核对规划文档、任务清单与本轮验收证据，列出未完成/未验证项。
2. 若仍有本轮必需的失败项，不标记完成、不归档；先报告待处理内容。
3. 条件满足后，按项目实际可用的 OpenSpec 流程同步主规格、校验并归档，核对归档路径与规则一致性。
4. 输出交付清单：代码、规格、运行说明、验收结果和已知限制；确认没有密钥或业务数据库混入提交。
5. 分别报告本地运行、打包、部署的真实状态。
本消息不授权新增公网发布或数据迁移；若需要发布，先列出具体目标与将公开的文件供确认。
看什么结果，才能继续？

应能从主规格查到最新规则，从归档找到变更过程；上线结论必须另有部署和访问验证。

结果不对时，如何追问

发现主规格遗漏时回复：“先完成规则同步和差异检查，再归档；不要只移动变更文件夹。”
