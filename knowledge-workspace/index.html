AI KNOWLEDGE OS · LLM WIKI · WORKSPACE

从“知识库”到“知识工作系统”

建立一套可持续编译、可追溯、可复用，并能真正进入业务工作的 AI 知识操作系统。Obsidian 可以加入，但不是底座。

AI Knowledge OS = Filesystem + Raw + LLM Wiki + Workspace + Skills + AGENTS.md + Harness
总模型LLM WikiWorkspaceObsidian知识飞轮提示词

01｜先把七个概念彻底分开

EVIDENCE

Raw

原始证据。文章、论文、网页、录音、AI 对话、项目材料。只新增、尽量不改、保留出处。

KNOWLEDGE

Wiki

AI 从 Raw 持续“编译”出的长期知识：概念、实体、综合主题、来源摘要与关系。

BUSINESS

Workspace

围绕业务目标建立的工作环境，例如 IP、新媒体、课程研发、咨询工作台。

CAPABILITY

Skill

把验证过的方法论变成可重复执行的 SOP：输入、步骤、工具、检查和输出标准。

GOVERNANCE

AGENTS.md

项目级 AI 说明书：知识路由、权限、来源、更新规则、输出规范和任务边界。

EXECUTION

Harness

Codex / Claude Code 等执行环境，读取 Workspace、Wiki、规则和 Skills 完成工作。

一句话：Filesystem 是底座，Raw 是证据，Wiki 是编译后的知识，Workspace 是业务环境，Skill 是能力，AGENTS.md 是治理，Codex 是执行 Harness。

02｜LLM Wiki：核心不是“存”，而是“编译”

传统笔记：资料 → 保存。LLM Wiki：资料 → 原始证据 → AI 编译 → 长期知识。

文章 / PDF / 录音 / AI 对话 → Raw → AI Compiler → Concepts / Entities / Syntheses / Sources → Wiki
AI-Wiki/
├── raw/
│   ├── articles/ papers/ clips/
│   ├── transcripts/
│   └── conversations/
├── wiki/
│   ├── index.md
│   ├── log.md
│   ├── concepts/
│   ├── entities/
│   ├── syntheses/
│   └── sources/
├── outputs/
│   ├── qa/
│   └── health/
├── knowledge-candidates/
└── AGENTS.md
关键：一篇文章不等于一个 Wiki 页面。20 篇关于 Agent 的资料，可以持续编译进 Agent.md、Skill.md、MCP.md、Harness.md 等长期概念页。

03｜LLM Wiki 再往前一步：LLM Workspace

Wiki 负责长大

吸收资料、去重、连接概念、保留来源、发现冲突、更新长期知识。

Workspace 负责干活

写文章、做课程、咨询、研究和交付，同时调用多个 Wiki 与 Skill。

Wiki 负责“长大” · Workspace 负责“用 Wiki 干活”

推荐：两个长期 Wiki + 一个 IP Workspace

Knowledge/
├── AI-Domain-Wiki/              # AI专业知识唯一真源
│   ├── raw/  wiki/  outputs/
│   ├── knowledge-candidates/
│   └── AGENTS.md
└── Media-Methodology-Wiki/      # 新媒体方法论唯一真源
    ├── raw/  wiki/  outputs/
    ├── knowledge-candidates/
    └── AGENTS.md

Workspaces/IP-Workbench/
├── AGENTS.md                    # 总编辑 / 总调度
├── knowledge/
│   ├── ai-domain/               # → AI-Domain-Wiki/wiki
│   └── methodology/             # → Media-Methodology-Wiki/wiki
├── skills/
│   ├── topic-selection/ research/
│   ├── wechat-writing/
│   ├── xiaohongshu-writing/
│   ├── short-video/
│   ├── fact-check/
│   └── repurpose/
├── sources/                     # 当前任务上下文
├── projects/
├── outputs/
└── archive/
专业 Wiki：写什么。 方法论 Wiki：怎么思考、怎么表达。 Skill：怎么稳定执行。 Sources：这次具体发生了什么。

04｜Raw、Sources、Outputs 必须分层

层定位生命周期
Wiki / raw长期原始证据长期保存
Workspace / sources当前任务上下文项目级
Workspace / outputs文章、报告、脚本等工作产品成果资产
knowledge-candidates值得沉淀但尚未核验的候选知识核验后进入 Wiki 或淘汰
Raw = Evidence · Wiki = Compiled Knowledge · Output = Work Product

05｜Obsidian 是可选的人类 Knowledge IDE

AI VIEW

Codex

读取、搜索、编译、重构、更新、健康检查、调用 Skill、生成成果。

HUMAN VIEW

Obsidian

阅读、检索、双向链接、反向链接、知识图谱、人工判断和编辑。不是底层数据格式。

推荐：不要“在 Obsidian 里建设知识库”，而要“建设标准 Markdown LLM Wiki，然后选择用 Obsidian 打开它”。
Filesystem First · Markdown First · Obsidian Optional

共享 Wiki 可通过软链接进入多个 Workspace

Knowledge/
├── AI-Wiki/      # 实体：唯一真源
└── Media-Wiki/   # 实体：唯一真源

IP-Workbench/knowledge/ai-domain          -> AI-Wiki/wiki/
Course-Workbench/knowledge/ai-domain      -> AI-Wiki/wiki/
Consulting-Workbench/knowledge/ai-domain  -> AI-Wiki/wiki/

Symlink 通常可像目录一样被本地工具读取，但权限、沙箱、Git、同步和跨机器环境可能区别处理，实际使用前应测试。

06｜最终闭环：知识飞轮

外部信息 → Raw → 编译 Wiki → Workspace 调用 → Outputs → 候选知识 → 核验 → 回写 Wiki

持续编译

新资料持续合并到已有概念、实体和综合页。

跨资料连接

发现共同主题、相互印证、冲突判断和潜在线索。

健康检查

扫描缺来源、重复、冲突、孤岛、过期判断和缺失概念。

安全阀：Outputs 不直接写入 Wiki。先进入 knowledge-candidates，做来源核验、去重和冲突检查，再升级为长期知识。

07｜六个核心提示词：可直接复制

跑通以后，不要长期依赖手工提示词：稳定规则应进入 AGENTS.md，稳定动作应逐步封装为 Skill。

提示词 1｜初始化 LLM Wiki
请帮我初始化一个 Markdown LLM Wiki。

目标：建立一个由 AI 持续维护、可追溯、可长期演进的知识库。

请创建：
raw/articles/、raw/papers/、raw/clips/、raw/transcripts/、raw/conversations/
wiki/concepts/、wiki/entities/、wiki/syntheses/、wiki/sources/
outputs/qa/、outputs/health/、knowledge-candidates/
以及 wiki/index.md、wiki/log.md、AGENTS.md。

核心规则：
1. raw/ 是原始证据，只新增，不删除、不覆盖。
2. wiki/ 是编译后的长期知识。
3. 重要判断尽量指向来源。
4. 新资料先生成来源摘要，再更新已有概念页；能更新旧页时不要重复新建。
5. 不确定的信息标记“待核验”，不得补编事实。
6. 每次编译后更新 index.md 和 log.md。
7. AI 生成的工作成果不得直接作为长期事实写入 wiki，应先进入 knowledge-candidates。
8. 完成后列出新增、修改和待核验文件。
提示词 2｜编译新增资料
请扫描 raw/ 中尚未编译的新增资料，并编译进 wiki/。

执行：
1. 为每份新资料生成 wiki/sources/ 来源摘要，保留原始路径与 source_url（如有）。
2. 提取重要概念、实体、方法和判断。
3. 优先更新已有 wiki 页面；只有确有新概念时才新建页面。
4. 建立必要的内部链接，并记录相互印证、补充或冲突的关系。
5. 事实与判断尽量指向来源；无法确认的内容标记“待核验”。
6. 更新 wiki/index.md 和 wiki/log.md。
7. 不修改 raw/ 原始资料。
8. 最后报告本次新增、更新、冲突和待核验项。
提示词 3｜基于知识库回答问题
请先读取 wiki/index.md 了解知识库全貌，再根据 wiki/ 中已有内容回答：

[在这里写问题]

要求：
1. 优先使用知识库中已有知识，不要把互联网常识伪装成库内知识。
2. 指明答案依据了哪些 wiki 页面及其来源。
3. 区分“已有证据”“综合推断”“待核验”。
4. 如果知识库证据不足，明确告诉我缺什么。
5. 如果这个问题形成了有长期价值的综合结论，把答案保存到 outputs/qa/，不要直接写入 wiki。
提示词 4｜Wiki 健康检查
请对当前 LLM Wiki 做一次健康检查。

重点检查：
1. 哪些页面缺少来源或来源不可追溯。
2. 哪些概念重复、定义冲突或边界不清。
3. 哪些页面几乎没有链接，形成知识孤岛。
4. 哪些重要概念被多次提到，但还没有独立页面。
5. 哪些判断可能过期，需要重新核验。
6. 哪些综合页长期没有吸收新增资料。
7. index.md 是否真实反映当前知识结构。

请把报告保存到 outputs/health/。
按优先级列出最值得修复的 5 个问题。
除非我明确授权，不要在健康检查阶段直接大规模改写 Wiki。
提示词 5｜IP Workspace 总调度
你是本 IP Workspace 的 AI 总编辑。

处理内容任务时：
1. 先读取当前项目 sources/，确定本次事实、素材和任务目标。
2. 涉及 AI 概念、案例和专业判断时，查询 knowledge/ai-domain/。
3. 涉及选题、标题、结构、平台表达时，查询 knowledge/methodology/。
4. 根据目标平台调用 skills/ 中对应 Skill。
5. 明确区分：当前素材事实、长期 Wiki 知识、方法论规则、AI 新推断。
6. 具体人物、数字、日期和事件优先服从 sources/ 中可追溯证据。
7. 输出写入当前 project 或 outputs/。
8. 单次创作不得因为方便而直接修改共享 Wiki。
9. 发现值得长期沉淀的新知识时，写入 knowledge-candidates/，说明来源、价值和建议归属。
10. 如果知识不足，明确指出缺口，不要编造。
提示词 6｜成果回流长期知识
请检查 knowledge-candidates/ 中尚未处理的候选知识，判断哪些值得进入长期 Wiki。

对每条候选内容执行：
1. 找到其原始证据或可追溯来源。
2. 判断它是事实、观点、方法、案例还是推断。
3. 与现有 Wiki 去重。
4. 检查是否与已有知识冲突；有冲突时保留双方依据，不要强行合并。
5. 只有证据充分且具有长期复用价值时才写入 Wiki。
6. 优先更新已有页面，而不是制造重复页面。
7. 更新 index.md 和 log.md。
8. 无法核验的候选内容继续保留并标记“待核验”。

最后给出：已吸收、已合并、存在冲突、待核验、已淘汰五类清单。

08｜最后记住这四句话

知识是共享基础设施

长期 Wiki 维护唯一真源，不围绕每个项目复制一套。

Workspace 是业务环境

IP、课程、咨询、研究可以拥有不同工作台，同时共享知识。

Skill 是执行能力

稳定的方法从 Wiki 中逐渐“毕业”，变成可重复执行的能力。

Obsidian 是界面，不是地基

Markdown 与文件系统保证资产独立于具体软件；Codex 与 Obsidian只是不同客户端。

让知识活起来，更重要的是让活起来的知识进入工作。
