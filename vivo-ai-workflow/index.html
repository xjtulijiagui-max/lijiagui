MODULE 3 · 35 MIN

按 IPO 的 I → P → O，完成三段升级

模块2定义业务任务；模块3将已定义的任务变成可执行、可接力、可验收的工作过程。

3.1

补齐上下文：从输入资料到完整任务情境

Input · 8分钟
资料给得全，不代表任务讲得清。补角色、补背景、补目标，先确认能不能开始做。

方法与关键判断

  • 沿用 IPO 的 I：核对资料名称、来源、口径、质量、安全边界和待确认项。
  • 补 CHAT：C 谁来负责、AI 扮演什么角色；H 任务的业务背景、前序决策、样例和约束；A 本次交付目标及价值。
  • 明确“资料缺失怎么办”：影响执行的先提问或标待确认，禁止 AI 猜测补事实。

案例、互动与阶段产出

  • 从模块2的“项目跟进”IPO卡出发，补汇报对象、月度口径、项目状态、上期结论与本次目标。
  • 课堂第 5 分钟开始首次 AI 演示：让 AI 阅读任务卡，列“已知、待确认、可开始执行”的项目。
  • 学员将自己的 IPO 卡带入同一对话，核对或纠正 AI 的理解。
阶段产出：任务执行准备单（C/H/A 补充信息＋I 输入核对＋待确认清单）。
3.2

细化 T 中的 IPO：从一个任务到人机接力

Process → Task · 14分钟
T 不是重新写一遍 P，而是按需把总 IPO 的 P 细化为子 IPO，编排人机接力。

方法与关键判断

  • 以模块2总 IPO 的 P 为边界：对复杂处理步骤进一步拆分，每个子任务重新定义自己的 I（前置输入）、P（处理规则）、O（阶段输出与交接标准）。
  • T · Task = 子 IPO 的具体执行要求 + 任务依赖 + 人机分工 + 交接门槛；能并行的并行，有依赖的必须按顺序执行。
  • AI 承担授权范围内的整理、分析辅助和初稿；人保留材料授权、口径确认、关键判断与最终决定。

案例、互动与阶段产出

  • 拆“项目跟进”为材料核对 → 进度风险分析 → 人工业务判断 → 生成汇报 → 验收交付。
  • 展示“上一个子任务 O → 下一个子任务 I”的交接关系：只有满足验收与审批门槛才进入下一步。
  • 课堂只执行已满足前置条件的第一子任务；遇到缺失数据、未授权材料就停止并请求确认。
阶段产出：人机接力表（子任务 IPO＋依赖关系＋分工＋检查与交接门槛）及首个执行结果。
3.3

建立验收闭环：从输出标准到可信交付

Output · 13分钟
两级验收：每个子 IPO 的 O 决定能否交接；总 IPO 的 O 决定最终能否交付。

方法与关键判断

  • 先按每个子 IPO 的 O 检查阶段结果与交接条件，再沿用模块2总 IPO 的 O 验收最终交付物，不另造一套最终标准。
  • 用原始材料与业务规则逐项验证：数字口径、结论证据、问题覆盖、输出格式和人工决策点。
  • 对不合格项定位 I / P / O 原因并回退修复；AI 自检只是初步检查，最终由人验收。

案例、互动与阶段产出

  • 演示“口径不一致、结论缺依据、风险遗漏”三类常见问题。
  • 要求 AI 输出“标准—证据—状态—问题—修复动作”的验收记录，不得无依据自称通过。
  • 人工标记通过、退回或待确认；只纠正相关部分，复验后进入最终交付。
阶段产出：子 O 交接验收 + 总 O 终验记录、纠错回退清单与人工确认状态。
方法论速查

IPO 是业务任务内核，CHAT 是完整协同交代

先有业务逻辑，再为 AI 配齐角色、背景、目标和行动；执行时再增加接力与验收机制。

C · Character 角色

人是谁、AI 是什么助手、职责与审批权属于谁？重点补在 3.1。

H · History 背景

业务来龙去脉、已完成工作、规则、样例与约束；I 中的材料为其提供部分依据。重点补在 3.1。

A · Ambition：明确总目标；T · Task：递归细化与协同编排

A 说明为什么做、要取得什么业务成果；T 把模块2已确定的业务 IPO 转为可执行的子任务网络。

模块2 · 总 IPO：业务任务的完整定义
I总输入依据
P总处理流程（待细化）
O最终交付与验收标准
↓ 在 T 中按需细化 P，并组织人机协同 ↓
模块3 · T：多项可执行的子 IPO
子任务 1 · IPO₁I₁ → P₁ → O₁
子任务 2 · IPO₂I₂ → P₂ → O₂
子任务 3 · IPO₃I₃ → P₃ → O₃
O₁ → I₂ → O₂ → I₃：只是典型串行示例；实际可按业务依赖安排并行、判断与回退。
每个子 IPO 规定执行者与交接标准；各子任务通过后，仍须按总 O 完成终验。

准确理解：T 不是“IPO = T”，而是“总 IPO 中的 P → 若干子 IPO + 执行编排”。A 明确业务目标，C/H 为执行补足角色与上下文；简单任务无需强行拆分。子 O 用来把关交接，总 O 用来判断最终成果。

C

角色与权限

声明谁交代任务、AI 扮演什么角色、谁决定能否交付。

H

背景与依据

补时间、业务口径、过往结论和真实附件；无依据的不猜测。

A

目标与价值

说清本次想解决什么业务问题，成功的判断是什么。

T

子 IPO 与任务编排

把总 P 进一步细化成子 IPO，明确依赖、分工、交接及阶段验收。

课堂记忆：总 IPO 定义业务 → CHAT 补 C/H/A → T 将 P 按需细化为子 IPO 并编排接力 → 子 O 交接验收 + 总 O 最终验收。

方法来源：李家贵 IPO 与 CHAT 课程方法论；本页为教学重构，非 vivo 既有制度。

一案贯穿

“项目跟进”怎样从一张 IPO 任务卡变成一串人机任务？

总任务：I 项目台账 / 会议纪要 / 风险登记；P 核对、分析、判断、生成、验收；O 进展、风险和决策事项汇报（按任务卡标准）。

先明确：总 IPO 描述整项工作；模块3 CHAT 的 T 以总 P 为基础，按需展开成子 IPO，并增加人机分工、顺序依赖、交接标准和回退机制。这是“业务处理逻辑 → 可执行任务网络”的升级。
01资料收集与一致性核对I：已授权资料 → P：比对数据与缺漏 → O：核对清单人提供 / AI核对
02进度与风险初步分析以前一步核对通过的数据为输入，输出带证据的分析线索AI辅助
03业务判断与口径确认人判断风险级别、争议数据与待决策事项；未确认不下发定论人确认
04生成进展汇报初稿基于已确认信息按预定结构交付；并非必须生成 PPTAI起草
05逐项验收与交付依据原 O 标准查证、修订、复验，责任人确认后交付人终验

演示用模拟或已授权脱敏资料。真正的工作可能只有两步，也可能有更多分支；按自己的 IPO 实际情况调整，不复制示例中的业务结论。

35 分钟如何讲？

0—8分钟 · 3.1 补背景

拿出模块2任务卡；第5分钟 AI 首次读卡，补 C/H/A，确认 I 是否充分。

8—22分钟 · 3.2 做接力

展开 P 的子任务，确认谁做、谁判断、何时交接，并运行首个子任务。

22—35分钟 · 3.3 严验收

以 O 的标准核验实际结果，定位问题并回退修正；完成讲评答疑。

资料给得全，不代表任务讲得清；一个任务看 IPO，一串任务看接力；AI 生成的是结果，验收通过的才是成果。

连续跟练 · 复制即用

同一张 IPO 任务卡，连续使用三条提示词

在同一个 AI 对话中按 3.1 → 3.2 → 3.3 顺序使用，后一步接前一步的产出。以“项目跟进”为示例，真实课堂请换成你的岗位任务。特别注意：T 是总 IPO 的进一步任务化细分，而不是另起炉灶。

开始前：打开模块2 IPO 任务卡，使用你自己已核对的版本；只上传公开、模拟或已获准脱敏的内容。缺失信息标“待确认”，不要虚构制度、数字或来源。
3.1 · INPUT

补齐上下文：让 AI 先读懂 IPO，再决定能否开始

承接模块2已经核对的 I/P/O，不重拆工作。补充 C 角色、H 背景、A 目标，并检查输入是否充分，输出“任务执行准备单”。

你将协助我执行一项已经用 IPO 梳理过的真实工作。请先阅读我附上的《IPO任务卡》或以下粘贴的 IPO 内容。它已经由我初步核对，是此次执行的业务依据；不要重新设计整项工作。

【模块2已确认的 IPO 任务卡】
〖在此粘贴 I / P / O，或上传获准使用的任务卡〗

【补充 CHAT 协同上下文】

A · 本次目标：

请先做四件事，不要直接生成最终业务成果：
1. 用“已确认 IPO / 补充的 C-H-A / 待确认事项”三栏摘要，检查你对任务的理解。

3. 从原 IPO 的 P 和 O 中提取处理步骤及交付标准，不擅自改写；若发现冲突，指出并请求我决定。

3.2 · T / P

把总 P 细分成子 IPO，再做人机任务编排

在 CHAT 的 T · Task 中，依据总 IPO 的 P 拆出一个或多个子 IPO，每个节点都交代 I、P、O，再明确任务间的顺序、分工和阶段验收。

继续刚才同一个任务。请沿用已经确认的《总IPO任务卡》和 3.1 的《任务执行准备单》，不要重选任务，也不要擅自改变原 IPO 的总输入、业务规则或最终交付标准。

现在把 CHAT 的 T（Task）落实为“总 IPO 的进一步细分 + 人机任务编排”。

【第一步：从总 P 细化出子 IPO】
1. 先准确复述总 IPO：I（原始输入）、P（整体处理逻辑）、O（最终成果及验收标准）。
2. 检查总 P 是否包含多个相对独立的步骤、跨角色交接、判断分支或人工审批点。
3. 只在确有必要时拆成多个可执行子任务；简单任务保留一个 IPO 即可，不要为拆解而拆解。
4. 为每个子任务分别填写：
   - 子 I：需要哪些资料？来自总 I，还是前一子任务的 O？缺失时怎么办？
   - 子 P：具体处理动作、规则、工具及异常分支是什么？
   - 子 O：产出什么阶段结果？如何验证合格？谁确认后可以交接？
5. 保留“总 P 的原始步骤 → 子 IPO 编号”的对应关系，不能擅自删减业务环节。

【第二步：形成 T 的协同执行网络】
请输出《子 IPO 人机接力表》：
序号｜对应总 P 步骤｜子 I｜子 P｜子 O｜人/AI 执行者｜前置依赖｜交接标准｜人工确认点｜异常/回退方式。

编排要求：
- 上一子任务 O 经过必要核验后，才能成为依赖它的下一子任务 I；
- 标明哪些必须串行、哪些可独立并行，以及判断依据；
- AI 可以整理、比对、辅助分析和起草，但不能代替人作授权、业务口径和关键决策；
- 每个子任务 O 都需有可检查的交付门槛；所有子任务完成仍不代表总 O 自动验收通过。

【第三步：只执行当前可启动的子 IPO】
先判断最先启动的子任务是否具备资料、权限及前置条件。
具备时仅执行该子任务，给出阶段结果、证据来源、子 O 对照检查和需要我确认的交接事项。
不具备时输出阻塞原因并停止；不要假称已执行、已批准或已验收。

如以项目跟进为例，可出现“材料核对 IPO₁ → 风险分析 IPO₂ → 人工判断 IPO₃ → 汇报编制 IPO₄”；但请完全以我的总 IPO 实际内容为准。
3.3 · O / 验收

按原 O 标准验收：发现问题、回退修正、复验确认

验收分两层：子 IPO 的 O 检查阶段结果与交接条件；总 IPO 的 O 检查最终交付成果。AI 自检不替代人工复核。

继续同一项工作。请使用模块2《IPO任务卡》中原有的 O · Output 交付标准，并结合刚才《人机接力表》的阶段成果，对“实际已经生成的内容”执行验收。

请先提取原总 O 中的交付物、格式、质量标准、验收人；再读取 3.2《子 IPO 人机接力表》每一子 O 的交接标准。不要临时替换原总 O 标准。

执行两级验收：
- 第一级，按子 IPO 的 O 逐项检查阶段成果、证据与交接门槛；若前序子 O 未通过，不得认定依赖它的后续任务可交接。
- 第二级，按总 IPO 的 O 检查整项工作最终成果；即使每个子任务通过，也不能自动认定总成果通过。

输出《两级验收表》（标明“子任务阶段验收”或“总成果终验”），每项包含：
验收标准｜实际交付内容｜核对证据/来源｜状态（初检符合/不符合/待人工确认/无法判断）｜问题与责任人｜建议修复动作。

至少按任务卡适用情况检查：
1. 数字与业务口径是否与授权原始材料一致；
2. 结论是否有可核对的来源，是否存在推断冒充事实；
3. 风险、问题、待决策事项是否遗漏；
4. 内容结构、字段、格式是否符合原 O；
5. 每个子 IPO 的 O 是否满足真实交接门槛，子任务依赖是否有已核验的前序输出；
6. 原总 IPO 标记的人工检查点是否已经实际完成；最终成果是否满足原总 O。

发现问题时：
- 说明问题可能来自 I（输入错误/缺资料）、P（处理规则/步骤错误）还是 O（输出不符合标准）；
- 给出最小必要修改及修复依据；需要上游核对时，先请求人工补充或确认，不得直接编造“正确答案”；
- 对修正后的相关条目再次检查，并保留“初检结果 → 修订结果 → 复验状态”。

最后把结论分为：可提交人工终验 / 需要修订 / 因信息不足暂不能验收。
不得宣称“已经人工批准”或“全部合格”；请列出等待我确认的事项，最终验收与交付决定由我作出。

本模块最终交付的，不是三条孤立提示词

一张总 IPO 卡 → 一份 C/H/A 执行准备单 → T 中的子 IPO 接力表与阶段成果 → 子任务 O 与总 O 的两级验收记录 → 人工确认。验证有效后，再进入模块4沉淀 SOP 或 Skill。

授课收束：模块2训练“任务定义能力”，模块3训练“协同执行与验收能力”。AI 的价值不是生成一段看似完整的话，而是被组织成一个可靠的业务交付过程。
