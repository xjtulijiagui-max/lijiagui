从 IPO 到 CHAT：让 AI 从理解任务走向协同交付

—— vivo 全员 AI 实操技巧线上课程 · 模块三教学页

学习路径：选准场景 → 拆清任务 → 协同交付 → 固化复用　|　课堂安排：3.1 补背景 8 分钟 ＋ 3.2 做接力 14 分钟 ＋ 3.3 严验收 13 分钟

核心问题

模块2已经把任务拆成 IPO，如何让 AI 真正执行、交接并通过验收？

记忆点

3.1 补齐上下文，让 AI 懂业务；3.2 设计人机接力，让 AI 会做事；3.3 建立验收闭环，让 AI 做对事。

模块2把任务拆清楚，模块3把任务做出来、验到位

只带入一份已经核对的 IPO 任务卡：从静态业务逻辑，进入动态人机协同。

MODULE 3 · CHAT 协同执行

补上下文 · 做人机接力 · 真正验收

沿着原 IPO，补齐协同条件，把 P 拆为可接力的子任务，依据 O 的标准检查真实结果。

课程关键判断：IPO 是任务的业务内核，CHAT 是全面深入的协同交代框架。IPO 主要为 CHAT 的 A（目标）和 T（行动）提供业务依据，但并不机械等同于 AT；输入材料与 H（背景）也有关联。
不换场景不重做 IPO同一对话连续跟练最终由人确认交付
MODULE 3 · 35 MIN

按 IPO 的 I → P → O，完成三段升级

模块2定义业务任务；模块3将已定义的任务变成可执行、可接力、可验收的工作过程。

3.1

补齐上下文：从输入资料到完整任务情境

Input · 8分钟
资料给得全，不代表任务讲得清。补角色、补背景、补目标，先确认能不能开始做。

方法与关键判断

  • 沿用 IPO 的 I：核对资料名称、来源、口径、质量、安全边界和待确认项。
  • 补 CHAT：C 谁来负责、AI 扮演什么角色；H 任务的业务背景、前序决策、样例和约束；A 本次交付目标及价值。
  • 明确“资料缺失怎么办”：影响执行的先提问或标待确认，禁止 AI 猜测补事实。

案例、互动与阶段产出

  • 从模块2的“项目跟进”IPO卡出发，补汇报对象、月度口径、项目状态、上期结论与本次目标。
  • 课堂第 5 分钟开始首次 AI 演示：让 AI 阅读任务卡，列“已知、待确认、可开始执行”的项目。
  • 学员将自己的 IPO 卡带入同一对话，核对或纠正 AI 的理解。
阶段产出：任务执行准备单（C/H/A 补充信息＋I 输入核对＋待确认清单）。
3.2

设计人机接力：从业务步骤到多任务协同

Process · 14分钟
一个任务看 IPO，一串任务看接力。先按 P 拆子任务，再明确谁做、谁判断、何时交接。

方法与关键判断

  • 沿用 IPO 的 P：识别顺序、判断规则、异常分支和人工检查点；复杂步骤可继续拆成子 IPO。
  • 将任务串联为“任务—负责人—前置输入—交付输出—交接条件”，辨别可并行与必须串行的步骤。
  • AI 承担授权范围内的整理、分析辅助和初稿；人保留材料授权、口径确认、关键判断与最终决定。

案例、互动与阶段产出

  • 拆“项目跟进”为材料核对 → 进度风险分析 → 人工业务判断 → 生成汇报 → 验收交付。
  • 展示从 AI 到人的交接：前一步有核验结果，才能进入依赖它的下一步。
  • 课堂只执行已满足前置条件的第一子任务；遇到缺失数据、未授权材料就停止并请求确认。
阶段产出：人机接力表（子任务 IPO＋依赖关系＋分工＋检查与交接门槛）及首个执行结果。
3.3

建立验收闭环：从输出标准到可信交付

Output · 13分钟
AI 生成的是结果，验收通过的才是成果。定义“什么叫合格”和证明“实际合格”是两件事。

方法与关键判断

  • 沿用 IPO 的 O：交付物、对象、格式、质量标准及验收责任人，不另造一套标准。
  • 用原始材料与业务规则逐项验证：数字口径、结论证据、问题覆盖、输出格式和人工决策点。
  • 对不合格项定位 I / P / O 原因并回退修复；AI 自检只是初步检查，最终由人验收。

案例、互动与阶段产出

  • 演示“口径不一致、结论缺依据、风险遗漏”三类常见问题。
  • 要求 AI 输出“标准—证据—状态—问题—修复动作”的验收记录，不得无依据自称通过。
  • 人工标记通过、退回或待确认；只纠正相关部分，复验后进入最终交付。
阶段产出：对照原 O 标准的验收表、纠错记录和人工确认状态。
方法论速查

IPO 是业务任务内核，CHAT 是完整协同交代

先有业务逻辑，再为 AI 配齐角色、背景、目标和行动；执行时再增加接力与验收机制。

C · Character 角色

人是谁、AI 是什么助手、职责与审批权属于谁？重点补在 3.1。

H · History 背景

业务来龙去脉、已完成工作、规则、样例与约束；I 中的材料为其提供部分依据。重点补在 3.1。

A · Ambition 目标 + T · Task 行动

业务目标告诉 AI 为何而做；具体行动则须承载真实业务任务的输入、处理、输出。

IInput · 输入依据
PProcess · 处理逻辑
OOutput · 交付标准

准确理解：IPO 主要提供 A / T 的业务内核，不等于 CHAT 的全部；H 也需要 I 中资料和前序信息支撑。多任务接力与验收闭环，是让 CHAT 真正落地的执行机制。

C

角色与权限

声明谁交代任务、AI 扮演什么角色、谁决定能否交付。

H

背景与依据

补时间、业务口径、过往结论和真实附件；无依据的不猜测。

A

目标与价值

说清本次想解决什么业务问题，成功的判断是什么。

T

行动与交付

沿 IPO 的 P 组织行动，沿 O 明确交付内容、标准及验收方式。

课堂记忆：IPO 把工作拆清楚 → CHAT 把任务交代清楚 → 人机接力把流程做起来 → 验收闭环把成果验到位。

方法来源：李家贵 IPO 与 CHAT 课程方法论；本页为教学重构，非 vivo 既有制度。

一案贯穿

“项目跟进”怎样从一张 IPO 任务卡变成一串人机任务？

总任务：I 项目台账 / 会议纪要 / 风险登记；P 核对、分析、判断、生成、验收；O 进展、风险和决策事项汇报（按任务卡标准）。

先明确：任务可以逐层拆解。总 IPO 描述整项工作；当 P 包含多步骤、多角色或关键检查点时，再展开子任务，每个子任务也能用 IPO 结构描述。
01资料收集与一致性核对I：已授权资料 → P：比对数据与缺漏 → O：核对清单人提供 / AI核对
02进度与风险初步分析以前一步核对通过的数据为输入，输出带证据的分析线索AI辅助
03业务判断与口径确认人判断风险级别、争议数据与待决策事项；未确认不下发定论人确认
04生成进展汇报初稿基于已确认信息按预定结构交付；并非必须生成 PPTAI起草
05逐项验收与交付依据原 O 标准查证、修订、复验，责任人确认后交付人终验

演示用模拟或已授权脱敏资料。真正的工作可能只有两步，也可能有更多分支；按自己的 IPO 实际情况调整，不复制示例中的业务结论。

35 分钟如何讲？

0—8分钟 · 3.1 补背景

拿出模块2任务卡；第5分钟 AI 首次读卡，补 C/H/A，确认 I 是否充分。

8—22分钟 · 3.2 做接力

展开 P 的子任务，确认谁做、谁判断、何时交接，并运行首个子任务。

22—35分钟 · 3.3 严验收

以 O 的标准核验实际结果，定位问题并回退修正；完成讲评答疑。

资料给得全，不代表任务讲得清；一个任务看 IPO，一串任务看接力；AI 生成的是结果，验收通过的才是成果。

连续跟练 · 复制即用

同一张 IPO 任务卡，连续使用三条提示词

在同一个 AI 对话中按 3.1 → 3.2 → 3.3 顺序使用，后一步接前一步的产出。以“项目跟进”为示例，真实课堂请换成你的岗位任务。

开始前：打开模块2 IPO 任务卡，使用你自己已核对的版本；只上传公开、模拟或已获准脱敏的内容。缺失信息标“待确认”，不要虚构制度、数字或来源。
3.1 · INPUT

补齐上下文：让 AI 先读懂 IPO，再决定能否开始

承接模块2已经核对的 I/P/O，不重拆工作。补充 C 角色、H 背景、A 目标，并检查输入是否充分，输出“任务执行准备单”。

你将协助我执行一项已经用 IPO 梳理过的真实工作。请先阅读我附上的《IPO任务卡》或以下粘贴的 IPO 内容。它已经由我初步核对，是此次执行的业务依据；不要重新设计整项工作。

【模块2已确认的 IPO 任务卡】
〖在此粘贴 I / P / O，或上传获准使用的任务卡〗

【补充 CHAT 协同上下文】
C · 角色：
- 我是〖岗位/职责〗，负责〖业务判断/审批职责〗；
- 你作为 AI 承担〖资料归纳/分析辅助/草稿生成等获准工作〗；
- 最终确认人是〖角色〗。

H · 背景：
- 当前业务背景及本次执行时间：〖背景与时间〗；
- 前序决策/上一期结果/重要业务规则：〖简述或标待确认〗；
- 可使用的材料和样例：〖列出获准资料及来源〗；
- 保密与权限限制：〖哪些不得输入或外发〗。

A · 本次目标：
- 我要解决的业务问题：〖具体问题〗；
- 交付对象、用途和期望价值：〖对象/使用情境/目的〗。

请先做四件事，不要直接生成最终业务成果：
1. 用“已确认 IPO / 补充的 C-H-A / 待确认事项”三栏摘要，检查你对任务的理解。
2. 检查 I 的资料、来源、口径、质量和权限是否充分；不足的具体标明，不要臆造。
3. 从原 IPO 的 P 和 O 中提取处理步骤及交付标准，不擅自改写；若发现冲突，指出并请求我决定。
4. 输出《任务执行准备单》：已具备条件、缺失信息、必须人工确认点、建议可启动的第一子任务。

最多提出 5 个影响执行的关键问题。若前置条件不满足，先暂停相关执行，等待我补充或确认。
3.2 · PROCESS

设计人机接力：把 IPO 的 P 转成可执行的子任务

在 3.1 准备单基础上展开 P：任务分解、依赖与并行、人机角色、交接门槛。不是单纯列“AI 做什么、人做什么”。

继续刚才同一个任务，沿用已经确认的《IPO任务卡》和《任务执行准备单》，不要重新选题、重写业务流程或改变未经我批准的业务口径。

现在进入 P · Process 的人机接力设计：

第一步：按原 IPO 的处理流程，判断是否需要拆成多个子任务。
- 每个子任务说明：子任务名称、I 输入、P 处理动作、O 阶段输出；
- 标注任务间依赖关系；确有依据才能并行，不能假设所有步骤可同时做；
- 遇到异常、资料缺失、判断冲突，明确停止或回退条件。

第二步：制作《人机接力表》，列出：
序号｜子任务 IPO｜前置条件｜执行者（人/AI/协同）｜交付结果｜人工检查点｜交接/验收门槛。

分工原则：
- AI 可以协助资料整理、信息比对、分析线索提取、结构组织和初稿编写；
- 我负责材料授权、事实与业务口径核定、关键判断和结果批准；
- 没有证据的结论标为“待核实”，不得伪造已经检查或已经执行的动作；
- 任何需人工确认的节点必须停下来，等我明确回复后才能推进。

第三步：请只执行“资料齐全、权限明确、前置条件已满足”的第一个子任务。
先输出该子任务的实际结果、来源依据与未解决问题，不要跳过人工检查点自动运行全流程。

案例提醒：如果我的任务是项目跟进，可能需要先核对台账，再分析风险、人工确认口径、生成汇报、最终验收；若我的 IPO 不是这一流程，以我的任务卡为准。
3.3 · OUTPUT

按原 O 标准验收：发现问题、回退修正、复验确认

“有验收标准”还不够，必须执行验收并留下证据。AI 自检不替代人工复核，尤其是数字、事实与业务判断。

继续同一项工作。请使用模块2《IPO任务卡》中原有的 O · Output 交付标准，并结合刚才《人机接力表》的阶段成果，对“实际已经生成的内容”执行验收。

请先提取原 O 中的交付物、格式、质量标准、验收人；不要临时替换成另一套标准。

输出《交付验收表》，每项包含：
验收标准｜实际交付内容｜核对证据/来源｜状态（初检符合/不符合/待人工确认/无法判断）｜问题与责任人｜建议修复动作。

至少按任务卡适用情况检查：
1. 数字与业务口径是否与授权原始材料一致；
2. 结论是否有可核对的来源，是否存在推断冒充事实；
3. 风险、问题、待决策事项是否遗漏；
4. 内容结构、字段、格式是否符合原 O；
5. 原 IPO 标记的人工检查点是否已经实际完成。

发现问题时：
- 说明问题可能来自 I（输入错误/缺资料）、P（处理规则/步骤错误）还是 O（输出不符合标准）；
- 给出最小必要修改及修复依据；需要上游核对时，先请求人工补充或确认，不得直接编造“正确答案”；
- 对修正后的相关条目再次检查，并保留“初检结果 → 修订结果 → 复验状态”。

最后把结论分为：可提交人工终验 / 需要修订 / 因信息不足暂不能验收。
不得宣称“已经人工批准”或“全部合格”；请列出等待我确认的事项，最终验收与交付决定由我作出。

本模块最终交付的，不是三条孤立提示词

一张 IPO 卡 → 一份执行准备单 → 一张人机接力表及阶段结果 → 一份有证据的验收记录 → 人工确认。验证有效后，再进入模块4沉淀 SOP 或 Skill。

授课收束：模块2训练“任务定义能力”，模块3训练“协同执行与验收能力”。AI 的价值不是生成一段看似完整的话，而是被组织成一个可靠的业务交付过程。
