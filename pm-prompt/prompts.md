# 产品经理沟通：22组可复制提示词

整理改写版。将【】替换为真实材料，核对草稿后再使用。

## 基础表达

### P01 把客户反馈写准确

走访结束，需要把客户反馈准确同步给团队。

```text
你是产品经理的沟通助手。请整理一段客户反馈。
背景：我向【目标角色】介绍【产品/功能】，需要把反馈同步给【接收人】。
原始反馈：【粘贴客户原话与观察记录】。
输出：80字左右的书面表达，依次写客户认可点、具体顾虑、待确认问题。
保留客户原意；区分原话与推测，不把顾虑改写成认可。
```

### P02 把汇报改成结论先行

向负责人汇报，需要把过程压成结论与请求。

```text
请将下面的产品工作汇报改成结论先行。
背景：我是【产品经理角色】，向【汇报对象】说明【本次目标】。
原稿：【粘贴草稿及已核实的数据】。
输出三条：当前结论、关键依据、需要对方决定或支持的事项。每条不超过30字，用表格呈现。
没有数据不要补造；缺少行动诉求时，请单列待补问题。
```

### P03 用MECE整理进度与问题

项目状态和风险混在一起，需要重新分类。

```text
请把【项目事实清单】整理成便于管理者判断的汇报。
背景：项目为【名称】，汇报对象为【角色】，截止时间为【日期】。
先按已完成、进行中、待启动分类，每项只出现一次；另列风险、影响与应对表，用事项编号关联。
输出：一句总体结论、事项状态表、风险表、需决策事项。
检查分类是否重叠或遗漏。未完成的事项不可写成成果，风险不要和状态混为同一分类。
```

### P04 用PREP提出一个建议

跨部门会议上，希望提出一个有依据的建议。

```text
请用PREP组织我的跨部门发言。
背景：【会议议题、参会角色、我希望推动的决定】。
观点：【一句建议】；依据：【已核实的理由、数据或案例】。
输出：观点、理由、例证、重申与行动建议四段，再合成100字以内的口语发言。
理由要回应对方的目标。没有证据请标明待补，不生成虚构客户案例。
```

### P05 把AI变成异议陪练

正式沟通前，练习回应成本、能力或方案方面的质疑。

```text
你是产品沟通教练，同时扮演客户。
背景：【客户行业、角色、痛点、已知顾虑】；产品：【功能及已验证能力】；本次目标：【下一步动作】。
先用PREP写100字内的表达草稿。
再按友好、中性、强质疑三个难度逐轮提问，每次只问一个问题，等我回答后继续。
每轮按是否理解顾虑、是否给出证据、是否提出可行下一步点评，并给一版改写。
不得预设客户一定接受，不得虚构产品能力。
```

### P08 从真实经历提炼STAR案例

把一次工作经历整理成有事实依据的案例。

```text
请从以下工作经历提炼一个STAR案例。
输入：【真实经历、参与角色、时间、过程、结果证据】。
输出S情境、T任务、A我的关键行动、R结果，分别写清背景、具体目标、本人贡献和可验证变化。
把团队行动与个人行动分开；结果注明基线、周期和来源。
缺失字段列为待补问题，不补写成功结果。
```

## 客户沟通

### P06 从走访记录提炼下一步

客户拜访结束，需要留下明确的跟进行动。

```text
请整理客户走访纪要。
背景：【客户、参会角色、拜访目标与日期】。
输入：【客户原话、现场观察、已确认事项】。
按客户痛点、我方建议、下一步跟进输出，并列出原话证据。
每个跟进项写动作、负责人、时间和需要客户确认的内容；缺失项写待确认。
我方建议与客户承诺分开，不把沉默或口头兴趣当成确认。
```

### P09 把STAR案例讲成客户听得懂的故事

用已核实的案例向客户说明产品如何解决问题。

```text
请把下面的STAR案例改成面向【客户角色】的产品故事。
输入：【已核实STAR案例】；本次要说明的功能：【功能】。
按原有场景、具体困难、采取的动作、结果与适用条件组织，写成一段自然的对话脚本。
开头用一个客户能回答的问题，结尾邀请对方确认是否有类似情况。
只使用输入中的数据和引语，没有结果证据时不要宣称已见效。
```

### P10 生成客户走访预案

初次拜访前，准备开场、追问与可能的异议。

```text
你是B2B产品经理的访前助手。
客户信息：【行业、规模、业务流程、已有系统、已知需求碎片】。
拜访对象：【角色】；目标：【希望推进的下一步】。
输出三个开场切入点、五项可能异议，以及每项的澄清问题和应答草稿。
分别标明已知事实、待验证假设和需要现场追问的问题。
话术回应对方业务，不预设更换系统；未核实能力与收益不要写入承诺。
```

### P11 按决策角色准备沟通策略

同一客户有多个决策角色，需要分别准备沟通策略。

```text
请生成一份产品访前预案卡。
输入：【客户行业、规模、已知痛点、已有系统、决策角色及已知关注点】。
输出三个待验证的业务痛点；为HR、财务、IT、业务负责人等实际参与角色分别列出关注点、沟通语言、破冰问题、证据需求。
客户未说过的话只能标为模拟表达；不得伪造成原话。
最后列出影响采购或试点决策的未知信息，以及现场验证方法。
```

### P12 生成宣讲、异议与回访话术

产品宣讲前，一并准备故事、应答和后续联系。

```text
你是产品沟通教练。请准备一次产品宣讲。
输入：【三个功能点、目标客户、真实案例与收益证据、常见质疑】。
输出三段场景对话：客户困难、功能如何介入、已有证据与适用条件。
针对“已有系统”“太贵”等实际质疑，按理解顾虑、提供证据、提出低风险下一步写应答。
再写80字内的回访微信和80字内的邮件正文。
没有量化证据就写待验证指标，不虚构节省比例、接口能力或回本周期。
```

## 内部协同

### P07 写一封对方愿意回应的邮件

需要另一个部门投入资源或共同推进任务。

```text
请帮我起草跨部门协作邮件。
收件人：【角色】；共同目标：【对方关心的指标或任务】；原稿：【粘贴草稿】。
已核实依据：【数据、口径、来源】；希望支持：【具体动作、所需资源、截止时间】。
输出正式结构版和简短口语版；开头直接写合作建议，随后写对方收益、依据、双方分工和待确认事项。
再指出原稿最影响理解的三个问题。不要补造收益数字或替收件人承诺资源。
```

## 向上汇报

### P21 一分钟说清进展与决策

时间有限，需要让负责人快速判断进展与决策事项。

```text
把下面项目进展改成一分钟可读完的汇报。
输入：【进展、已核实数据、阻塞、影响、建议方案】；听众：【负责人】。
结构：一句目前状态、三条关键事实、需要领导决定的一件事。
决策项写清动作、负责人或授权对象、最晚时间；没有决策需求就明确只同步信息。
事实与预测分开，不为了让状态好看隐去风险，也不添加输入之外的业绩。
```

### P22 汇报风险时给出具体请求

风险出现迹象，需要及时提出有依据的支持请求。

```text
请生成一段风险沟通稿。
输入：【目前状态、风险迹象、影响范围、最晚决策时间、已采取措施、可选方案】。
按目前状态、风险与不处理的后果、请领导拍板的一件事输出。
需要补充的依据另列，不塞进主稿。风险未发生时用条件表达，预测说明依据。
诉求必须具体、在对方权限内、有明确时限；涉及承诺的时间以已确认口径为准。
```

## 项目交付

### P13 把销售承诺转成实施范围

销售向实施交接，需要确认承诺、范围与验收口径。

```text
你是产品项目交接助手。
输入：【销售承诺原文、已签范围、产品能力、客户新增期待、资源与时间约束】。
逐项输出已承诺范围、明确排除项、待评估项、验收口径与责任人。
生成客户、销售、产品与实施交接议程，必须确认承诺基线、范围边界、责任与里程碑。
再为超范围请求写一段话术：理解价值、说明本期边界、提出替代办法或评估路径。
没有正式确认的信息标为待确认，不替任何一方新增承诺。
```

### P14 把实施计划讲成客户里程碑

项目启动时，需要把实施计划讲成客户能理解的节点。

```text
你是产品项目启动助手。
输入：【阶段、时间、交付物、双方人员、依赖与已确认范围】。
输出客户视角的里程碑地图：每阶段能做什么、客户要配合什么、完成凭证是什么。
再给出20分钟启动会议程和RACI矩阵，明确负责R、最终负责A、咨询C、知会I。
每项只设一名A；角色尚未确定时标待确认。时间和交付物以输入为准，不拼接不同案例的计划。
```

### P15 协商本期做、下期做或不做

客户提出新增需求，需要评估范围并协商安排。

```text
请协助评估实施中的新增需求【需求原话】。
输入：【合同/工作说明书、已确认需求、验收标准、现有能力、工作量与排期】。
先判断在范围内、范围外或信息不足，逐条引用依据。
分别给本期做的前提、下期做的安排、不做的原因与替代方案，以及对应客户话术。
成本、工期或安全影响未评估时标为待评估；任何调整经相关负责人确认后才能成为承诺。
```

### P16 同一阻塞写成内外两版稿

同一项目阻塞，需要分别向团队和客户同步。

```text
请把同一项目问题写成两版沟通稿。
事实：【问题、证据、影响、当前进展、下一次更新时间】；约束：【资源、范围、时间】。
对内给研发与实施：事实、影响、所需资源、建议方案、待决策事项。
对外给客户：理解诉求、说明已知影响、给出已确认的处理节奏与替代方案。
两版事实必须一致。内部未批准的排期不要对外承诺，未知原因不要归责。
```

## 验收上线

### P17 让客户按业务场景做UAT

准备用户验收测试，需要提供测试步骤和问题模板。

```text
请给客户测试人员写一份口语化UAT指南。
输入：【测试环境、登录方法、角色权限、业务场景、验收口径、反馈渠道】。
说明如何登录、按什么顺序测试、如何判断结果、遇到卡顿如何处理。
给问题模板：现象、操作步骤、预期与实际结果、发生时间、截图或录屏、影响范围。
最后给确认、修复、复测、关闭流程。不要虚构登录地址、账号或承诺修复时间。
```

### P18 生成上线前四方确认清单

上线前，需要客户、研发、实施与厂商逐项确认。

```text
请生成上线前客户、研发、配置实施、平台厂商的四方确认清单。
输入：【本期范围、测试结果、数据核对、培训记录、部署和回退方案】。
覆盖功能、数据、人员、应急四项；每项列确认问题、证据、责任人、状态及遗留事项。
状态为通过、不通过、带条件通过；附责任、完成期限及授权放行人。
判据遵循项目约定，不默认套用99.9%或其他阈值；证据不足时不能写已就绪。
```

## 冲突协调

### P19 把三方立场翻译成可协商条件

客户要功能、研发受约束、领导催上线，需要推动协商。

```text
请作为产品项目协调助手，分析客户要【功能】、研发认为【约束】、领导要求【时间目标】的冲突。
输入：【各方原话、范围、技术评估、排期和决策权限】。
分开列三方诉求、证据、不可变约束和待确认的让步空间。
提出可比较的方案，说明满足什么、牺牲什么、风险和确认人；再给沟通顺序。
方案必须经各方确认，不预设一定存在折中方案，也不把推测写成各方真实动机。
```

### P20 分角色练一次冲突调停

用真实冲突练习澄清、回应和调停。

```text
你是产品沟通陪练，依次扮演客户、研发、领导。
背景：【真实冲突与已知事实】；我的角色：【产品经理】。
每方用两三句带情绪但符合事实的话提出要求；说完一方停下来，等我回应后再进入下一方。
三轮后按澄清诉求、识别约束、提出选择、确认行动点评，给出更准确的调停表达。
不要替我回答，不把现实中未知的事实补进对话。
```
